# Post-mortem: a live exit that never reached the broker

**Date:** 15 July 2026
**Impact:** a live position was recorded as closed in the system while it was still open at the
broker.
**Detection:** end-of-session reconciliation between system state and broker state.
**Status:** fixed, with regression tests covering both root causes.

Trade identifiers, the instrument, the broker and all monetary figures are omitted. The
engineering is the point.

## What happened

A live exit runs in two broker calls. The resting stop order has to be cancelled first,
otherwise the exit and the stop can both fill and the account ends up short. So the sequence is
cancel, then place a market sell.

On this trade the cancel went through and the market sell never did. The system then recorded
the trade as closed. The position stayed open at the broker.

## Root cause 1: an idempotency key that was not unique enough

Every broker call goes through a gateway that keeps an acknowledgement registry, so that a
retried call does not place a second order. That is the right design. The key was wrong.

The key was `(event_id, action)`. One exit handler makes two broker calls, `cancel_order` and
then `place_market_sell`, and both run under the same exit action and the same event id. The
second call therefore hashed to the same key as the first, matched the cached entry, and
returned the cancel response without ever calling the broker.

The dedupe worked exactly as written. It deduplicated two calls that were never duplicates.

The fix was to include the function in the key: `(event_id, action, fn_name)`.

This reproduced on every single live exit that had to cancel a resting stop first. It was not a
race and not intermittent. It was deterministic, which is why it is worth writing up: the bug
had been sitting in a code path that had simply never been exercised live in that exact
sequence before.

## Root cause 2: close authority in the wrong place

The paper variant ran before the live variant and unconditionally marked the trade closed, using
the exit price the simulation had computed. It did not depend in any way on whether the live
broker call had confirmed anything.

So even with the first bug fixed, the system was recording live closes on simulated evidence.
The paper variant was acting as the auditor of a live trade it had no visibility into.

The fix moved close authority for live-eligible variants into the live exit handler, which now
requires a polled fill confirmation from the broker before it marks the trade closed.

## What I took from it

**Two bugs, one incident, and the second was the dangerous one.** The missing sell is obvious in
a reconciliation report. State that closes on simulated evidence is not obvious at all: the
system looks correct and consistent, and the only thing that disagrees with it is the broker.
That is the failure mode worth designing against, and it is why the reconciliation check that
caught this now runs as a matter of course rather than on suspicion.

**An idempotency key has to be derived from everything that makes the call distinct.** The
original key encoded the event and the intent but not the operation, so two genuinely different
operations became indistinguishable. Idempotency that is too coarse is not a weaker guarantee,
it is an incorrect one.

**Authority belongs to whoever can observe the truth.** Only the component talking to the broker
can know that a live order filled. Anything else asserting a live close is guessing.

## Regression tests

Both root causes are covered by tests written against the real code paths, in
`tests/test_incident_2026_07_15_live_exit.py`. Neither makes a network call. The file is named
for the date of the incident, which is the convention across this suite: when the system breaks
in production, the fix ships with a test named after the day it broke, so the failure cannot
come back quietly.
